## 已准备的波动统计

PC接收日志新增 `completed_t_s`，以接收器单调时钟记录每个CRC正确完整帧的完成时间。
不改变TCP数据/回执协议，不等待落盘或图像绘制；旧接收命令仍兼容。

统计工具 `pc_tools/throughput_statistics.py`：

```powershell
python .\pc_tools\throughput_statistics.py .\logs\long_core_8x_1200s_20261021.jsonl --window 5 --expected-length 99328
```

- 总平均吞吐：全部有效帧字节×8/接收器总时长，含启动、结束和帧间等待。
- 最大/最小：每5秒实际完成的有效字节×8/5秒；空窗计0，不剔除低速段。
- 波动：总体标准差、CV=标准差/窗口均值、P5/P95、峰峰值、零速窗口数。
- 最后不足5秒的短窗不参与最大/最小/标准差，但其有效字节仍计入总平均。
- 帧率：有效完整帧数/总时长，另提供每5秒窗口FPS。
- 检查每帧是否为99328 B；缺少时间戳的旧日志拒绝估算窗口，不能用旧的单帧socket读取速率冒充整体吞吐波动。

本次首轮0有效帧时，上述工具只能给出失败记录的0速率；这不代表ESP32的正常最大吞吐为0。
恢复源帧后，应使用新日志文件名重新开始完整测试。

## 8倍帧率的换算边界

8倍每线768点，每帧 `(768+8)×2×64=99328 B`，每个完整帧为0.794624 Mbit。
在不考虑其它阶段限制时，`FPS=有效Mbit/s÷0.794624`；实际还不能超过源端完整帧发布率。
例如只有在源端仍约13.6 FPS的前提下，输出上限才约为13.6 FPS、对应10.807 Mbit/s。
此前大帧约11.9 Mbit/s不能直接保证本次8倍达到14.98 FPS，本轮实际8倍帧率尚未测出。
