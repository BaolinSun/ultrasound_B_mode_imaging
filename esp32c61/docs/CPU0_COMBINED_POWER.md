# CPU0 面板：一键 TX/AFE 待机与唤醒

CPU0 面板新增“CPU0 待机”和“唤醒 CPU0”。这两个按钮仅组合操作现有 TX7332、AFE5832 电源流程，不直接改变 CPU0 时钟或 WFI 策略，不操作 CPU1。

## 顺序

|按钮|第一阶段|间隔|第二阶段|
|---|---|---|---|
|CPU0 待机|TX7332 待机，等待硬件确认成功|至少 1 秒|AFE5832 待机，等待确认|
|唤醒 CPU0|AFE5832 唤醒，等待恢复就绪|至少 1 秒|TX7332 唤醒，等待恢复就绪|

1 秒从第一颗芯片的操作成功确认之后开始计时，不是仅在发送请求之间延时。调用现有两阶段停扫、关闭高压、传输排空和恢复检查；没有跳过 DMA、PSRAM 槽位、DDR 租约或时钟同步确认。

双待机且原有硬件/中断/队列条件成立后，CPU0 自动进入 WFI。接收到唤醒操作的 UART 命令时 CPU0 已短暂醒来执行前台服务；第二颗芯片恢复后保持正常调度。按钮名称不意味着 CPU0 曾断电，也不保证每次一定进入 WFI，应观察实际计数。

**唤醒后扫描、高压和上传仍停止**，由用户明确恢复。此前发现的 AFE 恢复图像差异未因增加组合按钮而修复，见 [体模切换记录](AFE_TX_IMAGE_CYCLE_20261028.md)。

## 执行与失败

- 顺序和等待在 ESP32 后台控制任务中执行。浏览器关闭不会取消或拆开流程，也不会把浏览器计时精度作为硬件操作间隔。
- 一次仅接受一个组合操作，配置事务占用时拒绝；原独立 AFE/TX 控制仍可使用。混合状态可显式唤醒恢复，两颗均待机时待机按钮禁用，两颗均就绪时唤醒按钮禁用。
- 两步及等待期间保持上传准入关闭，禁止其他普通命令混入。全程保留高优先级 `HV DISABLE`，1 秒等待按不超过约 20 ms 的检查段响应关断/通信复位。
- 第一阶段失败不发送第二阶段；等待期间中断也不继续下一阶段。明确失败、结果未知分别保留，不自动重试、回滚电源状态或自动启动成像。
- 第二阶段失败可能留下“一颗已恢复、另一颗仍待机”的状态；查询各芯片后由用户显式操作恢复。就绪状态不代表模拟输出或成像质量测量通过。
- 现有会话/请求匹配及有界任务缓存继续生效，重复提交同一请求返回缓存结果，不重复执行。

## 接口与命令

复用 `/api/zynq/commands` 和任务查询接口，新增 **ESP32 本地编排命令**，每批只能一条：

```powershell
python .\pc_tools\zynq_wifi_control.py --device-ip 192.168.3.27 -c "CPU0 SLEEP"
python .\pc_tools\zynq_wifi_control.py --device-ip 192.168.3.27 -c "CPU0 WAKE"
```

不要将 `CPU0 SLEEP/WAKE` 作为原始 UART/USB 命令发给 PS；它们由 ESP32 转换为既有 TX/AFE 操作。成功回执分别为 `@ACK 0 CPU0_SLEEP sleep`、`@ACK 0 CPU0_WAKE ready`。不新增 NVS 设置或 USB 口令。

`/api/status` 的 `zynq_control` 新增 `cpu0_power_supported` 和 `cpu0_power_stage`，页面显示 TX 操作、等待 1 秒、AFE 操作及失败阶段。完成提示是上次操作结果，当前芯片和 CPU 状态仍以各自缓存快照为准。

## 更新与验证

**仅更新 ESP32 固件，并强制刷新网页即可。无需更换 Zynq 应用、bit/XSA、FSBL 或 BOOT.BIN。** 使用当前正常的 combined 构建命令 `.\build.ps1`，固件在 `esp32c61/build-throughput-fast-socket-exp-combined/ultrasound_psram_udp.bin`。

本轮只做离线软件验证和构建，不连接/烧录板卡、不切换电源、不启动扫描或高压。测试覆盖正常顺序、从确认之后计时至少 1 秒、整个流程准入门控、重复请求/重复显式操作、配置冲突、两个阶段双向失败、等待期间优先关断/通信复位、网页互锁及回执不匹配。真实芯片切换、WFI 计数、模拟恢复和图像质量仍需板测。
