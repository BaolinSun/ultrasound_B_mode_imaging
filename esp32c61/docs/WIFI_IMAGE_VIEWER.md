# Wi-Fi 超声图像实时网页显示

## 启动

在 `D:\MyProjects\zynq_prj\ultrasound_B_mode_imaging\esp32c61` 中执行：

```powershell
python .\pc_tools\bmode_web_viewer.py --device-ip 192.168.3.27
```

打开 **http://127.0.0.1:8080/**，点击“开始接收”。运行程序或打开页面本身不会上传。

也可在同一台 PC 打开 **http://192.168.3.27/**，点击页面顶部“实时超声图像”卡片的“打开实时图像显示”，会在新标签页打开上述 PC 图像页，原 ESP32 配置页保留。先运行 Python，再点击入口；随后在图像页点击“开始接收”，不需另按 ESP32 页的 SDIO 单帧或连续测试。

该入口仅提供跳转，不把图像服务移到 ESP32，也不自动运行 PC 程序、开启高压或启动扫描。`127.0.0.1` 是浏览器所在电脑，不能用手机或其他电脑通过此入口查看接收电脑。自定义 `--http-port` 时直接使用 Python 打印的地址。

新增入口需要编译并更新 ESP32 固件；Zynq、bit、XSA、BOOT.BIN 及图像协议无需改变。仅重启 PC Python 不会更新 ESP32 的内嵌网页。
网页由 PC 提供，不是 ESP32 的 `192.168.3.27` 配置页，默认仅本机浏览器可访问。
电池供电时正常使用，不需要 USB、monitor 或控制口令。

首次运行如缺少显示依赖，执行一次：

```powershell
python -m pip install -r .\pc_tools\requirements-viewer.txt
```

仅依赖 NumPy、Pillow 和 Python 标准库；不需要 Qt、OpenCV、USB 驱动或参考工程。
PC 显示服务本身不要求修改固件；若要使用新增的 ESP32 页面入口，需要更新 ESP32 固件。不需要更新 Zynq，也不生成新 bit、XSA 或 BOOT.BIN。

## 操作流程

1. 保持当前成像固件及 ESP32 正常运行，Zynq 已建立 SDIO 握手。
2. 在 ESP32 原配置页把图像上传目标设置为**运行本程序的 PC 的 IP**，端口默认 `50001`。
   如果未设置正确，显示页会给出所需地址并拒绝启动，不会代写配置。
3. 关闭占用 `50001` 的旧 TCP/UDP 接收脚本。图像页自动识别固件选择的 TCP 或 UDP。
4. 按已有安全流程启动成像；新图像页不执行扫描、高压或参数命令。
5. 启动上述 Python 程序，打开本地网页，点击“开始接收”。程序先监听，再启动连续 SDIO 上传。
6. 首次收齐 64 条合法行后显示扇形图像。冻结只影响本页面，后台仍接收并确认数据；继续显示时获取最新图像。
7. 点击“停止接收”，或在 Python 终端按 `Ctrl+C`，程序停止自己启动的上传并关闭接收。

**停止接收不等于停止扫描或关闭高压。** 结束成像仍须通过原有控制入口执行相应安全操作。
关闭浏览器窗口不会停止后台上传；请先点击“停止接收”，或在 Python 终端按 `Ctrl+C`。
不要同时从原页面和显示页控制同一轮 SDIO 上传。设备原本已有上传时，新程序拒绝接管。

如需改变监听端口（不改变图像参数）：

```powershell
python .\pc_tools\bmode_web_viewer.py --device-ip 192.168.3.27 --port 50001 --http-port 8081
```

此时打开 `http://127.0.0.1:8081/`。多网卡需要指定接收网卡时可增加 `--data-bind <PC网卡IPv4>`；
设备目标必须与该地址及 `--port` 一致。默认数据监听 `0.0.0.0:50001`，来源限定为指定 ESP32。

## 解包与固定图像处理

链路为：

`Zynq DDR → SDIO → ESP32 TCP/UDP → PC CRC 校验 → 行缓存 → B-mode → PNG → 浏览器`

- 接收 `787456` 字节载荷；TCP 使用 UBST/UBSA，UDP 使用 UBSD，不适用于原始 PSRAM UDP 自测。
- 行数据为小端无符号 16 位，行头 8 字；前两字 `0x1C00/0x1800`，第 3 字为逻辑行号 `0～63`。
  每行后接 6144 点，行头间距为 6152 字。合法相邻行头确认边界；末行可由前一行确认。
- 只使用完整合法行，同一载荷重复行号取最后一行。不同 DDR 片段不是连续字节流，不能拼接残缺行。
- 首次累计齐 64 行才绘图，此后按行号滚动替换。5 秒未更新的行过期；不齐全时暂停发布、保留并标记旧图。
  新会话或重新开始时清空行缓存和灰度平滑状态，不混用旧会话图像。
- 数据已经是参考工程使用的 Q2.14 对数值，不再进行包络检波或重复取对数。
- 固定 ±45°、120 mm 深度、25 MHz 采样率、1540 m/s 声速、4 MHz 探头频率；双线性扫描转换输出 `883×624` 灰度图。
- 沿用参考默认 TGC、45 dB 动态范围、+3 dB 亮度、1.0 对比度、−45 dB 噪声底，
  99.9 百分位参考及 0.15 时间平滑。接收完整 6144 点，只把显示范围限制到 120 mm。
- 参考灰度 LUT 独立保存于 `pc_tools/bmode_assets/graymap_lut.txt`，缺失或非法时明确报错，不静默换成线性 LUT。

实现参考 `D:\MyProjects\py_prj\ultrasound_dev_kit\usb_graymap_bmode_pipeline.py` 的纯计算逻辑，
未修改参考工程，不将其作为运行时依赖。LUT 与参考文件一致，SHA256：
`5EC048290144B8A4050D262AB1C36FB281C5A5D5AAFC2A172373C8EDE0F50B8C`。

## 状态、性能与异常

页面显示最近 5 秒的接收帧率、图像发布帧率、有效吞吐，以及行覆盖率、网络坏帧、非法数据报、
无合法行载荷、待处理队列丢弃和图像年龄。发布帧率是 PC 后台发布速率，冻结后仍可继续增长。

- TCP 收齐载荷并通过 CRC 后即回执，不等待图像处理或浏览器；图像格式错误与网络 CRC 错误分别统计。
- UDP 缺包、冲突和 CRC 错误帧丢弃，不影响下一帧。TCP 断开或协议校验失败会结束本轮，需用户重新开始。
- 处理队列最多两份载荷，拥塞时丢弃旧待处理项，图像最多发布 10 FPS；实际速率受输入数据影响。
  浏览器每次仅发起一个图像请求，不逐帧回放积压数据。
- 超过 30 秒没有有效网络载荷会停止本轮并报告错误。已接收到载荷但无合法行时，继续监听并显示解包错误计数，不伪造图像。
- 停止顺序为先标记计划停止，再请求 ESP32 停止、有限等待确认，最后关闭连接；停止未确认会明确报告。
- 网页或服务断开后，旧画面不标记为实时。图像处理失败会停止自己启动的上传；重启 Python 后再尝试。
- 默认不保存原始数据和图像。每秒状态日志自动写入 `esp32c61/logs/bmode-viewer-*.jsonl`，
  日志写入与数据接收/回执隔离。没有新增参数调节、下载或任意串口控制接口。

**当前 DDR 没有完整帧冻结和防覆盖保证：这里是滚动行图，不保证 64 行来自同一次采集。
CRC 正确只证明网络载荷完整，不证明图像一致性或成像正确性。**

现有两份历史 `image_capture/*.txt` 没有满足参考解析器要求的行头间距；它们用于异常输入测试，
不能作为正常图像验收样本。如果覆盖率一直为 0 而网络帧数持续增长，应检查新采集数据的行格式，
不要把 CRC 通过当成解包正确，也不要强行 reshape 绘图。
