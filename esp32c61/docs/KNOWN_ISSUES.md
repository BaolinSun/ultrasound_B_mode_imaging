# 当前已知问题

## ESP-HTTP-001：内部 SRAM 紧张时状态 JSON 分配失败

- 记录日期：2026-10-29。
- 状态：**未修复，按用户要求暂缓处理**。不能将正常通过一次测速视为已解决。
- 现象：ESP32 输出 `httpd_resp_send_err: 500 Internal Server Error - JSON allocation failed`，网页或 PC 状态查询收到 HTTP 500。
- 位置：`main/web_server.c` 的 `reply()`；创建 JSON 对象失败、`cJSON_PrintUnformatted()` 序列化分配失败共用同一句错误。目前日志不能区分具体分配阶段。
- 已确认配置：`CONFIG_SPIRAM_USE_CAPS_ALLOC=y`，未启用 `CONFIG_SPIRAM_USE_MALLOC`；cJSON 未安装自定义分配钩子，普通 malloc/realloc 使用内部内存。PSRAM 有空闲不等于 JSON 能分配成功。
- 最可能诱因：TCP/Wi-Fi 活跃时内部 SRAM 瞬时紧张或连续空闲块不足；完整状态含大量 cJSON 节点、字段名和动态扩容的输出缓冲。尚未定位失败瞬间的最大空闲块，不能确认碎片化或内存泄漏。
- 影响：一次状态查询失败不必然中止图像数据传输；网页可能短暂显示断连。`sdio_benchmark.py` 会记录查询失败，连续三次查询失败时停止测试。查询成功不保证所有字段添加均成功，字段添加返回值的完整检查也需后续核对。

2026-10-29 的 `throughput_base_60s` 记录：8 倍抽取、99328 B/帧，815 个有效帧、10.63 Mbit/s、13.38 FPS，无新增 CRC/通信错误或 SDIO 复位，测速查询失败列表为空。内部堆历史低水位 **2108 B** 在测试前已经存在，测试后不变；成功采样的最低当前空闲为 **16400 B**，PSRAM 空闲 513868 B（约 502 KiB）。这份日志没有捕获此前 HTTP 500 的失败瞬间，也不能排除其他网页请求曾失败。

后续方向（本次不实施）：

1. 区分 JSON 对象、字段、打印/扩容等失败阶段，记录内部堆当前空闲及最大连续空闲块。
2. 评估专用预分配缓冲/内存池或明确分配到 PSRAM，避免频繁占用及扩容内部堆；不直接修改全部模块的全局分配策略。
3. 检查字段添加失败，避免返回看似成功但缺字段的状态；保留现有控制失败与结果未知语义。
4. TCP 配置、PS/PL、图像协议暂不调整；减少查询频率只能缓解，不能代替修复。
